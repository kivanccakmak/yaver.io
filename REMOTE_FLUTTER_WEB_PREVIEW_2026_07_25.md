- The preview overlay stays on:
  - `Starting flutter dev server...`

## Code-Backed Facts

So the screenshot matches the local iOS metadata.

### The affected mobile screen is `mobile/app/(tabs)/apps.tsx`

- the preview overlay inside the `bundleUrl && !webPreviewContentLoaded` branch

This screen has its own `/dev/events` SSE reader. It is separate from `DevPreview.tsx`, which is exactly the cross-surface drift class called out in `CLAUDE.md`.

### The local code already contains fixes for earlier versions of this incident

The repo has recent comments and tests for the exact failure family:

- `desktop/agent/devserver.go` now forces `DevServerStatus.Building = true` while an active dev server exists but has not bound yet. Without that, mobile treats the server as inactive and never opens `/dev/events`.
- `desktop/agent/devserver.go` now fills empty `BundleURL` from `BundleURL("")` for all frameworks. Without that, Flutter can be serving but mobile waits forever for an address.
- `mobile/app/(tabs)/apps.tsx` now opens `/dev/events` while `running OR building`.
- `mobile/app/(tabs)/apps.tsx` now buffers partial SSE chunks instead of parsing each network read as complete lines.
- `mobile/app/(tabs)/apps.tsx` now consumes `snapshot.recentLogs`, not only live `log` frames.
- `desktop/agent/devserver_start_remedy_test.go` includes a real 2026-07-25 Flutter failure: missing `.env` asset in `pubspec.yaml`, and asserts the remedy names `.env`, `pubspec`, and the project path.

Those facts strongly suggest the failure in the screenshot is not just "Flutter is slow"; it is one of these:

1. build 471 does not actually include the local `apps.tsx` changes,
2. the remote Go agent is older than the local code and does not report `building` / `snapshot.recentLogs`,
3. the remote Go agent is current but `/dev/events` is unreachable/auth-broken over the chosen transport,
4. the dev server is failing before it produces stdout, and the error event is not reaching/rendering,
5. there is a remaining React Native fetch/header bug in this screen's direct `fetch(`${baseUrl}/dev/events`)` call.

### The Go agent already exposes its version

`desktop/agent/httpserver.go` handles `GET /info` and returns:

- `version`
- `hostname`
- `workDir`
- lifecycle information
- runner information

Mobile already has `quicClient.getInfo()` and several screens read it. Device rows also have optional `agentVersion`. Therefore the connected banner should display the remote Go agent version from the existing `/info` source, falling back to `activeDevice.agentVersion`.

## Most Likely Root Cause

The most likely cause is version skew between the TestFlight app and the remote Go agent.

Reasoning:

- The screenshot still shows `waiting for the first output from the box`.
- The local `apps.tsx` now treats `heartbeat` as proof-of-life and `snapshot.recentLogs` as log input.
- If the app build includes that code and the agent emits snapshots/heartbeats, the text should become either:
  - `last output Ns ago`, or
  - actual recent log lines.
- Seeing no output after 25 seconds means either the SSE never opened, the agent did not emit a usable frame, or the app build does not contain the new parser.

Because build 471 is known, the missing fact is the remote agent version. The UI currently hides it in the shared connection banner, which makes this harder to diagnose from the phone.

## React Native / Expo Browser-Lane Audit

### RN has three different preview lanes

Yaver has to keep these separate:

- Hermes Reload: React Native / Expo only. The Go agent builds a Hermes bytecode bundle through `/dev/build-native`, then the Yaver mobile app loads it into the native container.
- Browser Reload: serves a web target through a WebView. For Expo this is `npx expo start --web`. For Flutter it is `flutter run -d web-server`. For Vite/Next it is the normal web dev server.
- WebRTC Reload: streams a remote runtime from the dev box.

The failure class is when Browser Reload silently falls into Hermes logic or when RN-web reports "rendered" before React actually mounted.

### Current code gets the broad lane separation mostly right

Mobile start path:

- `mobile/src/lib/quic.ts` sends `{ platform: "web", caller: "web-ui" }` when `startDevServer({ web: true })` is used.
- `mobile/app/(tabs)/apps.tsx` uses `web: true` for the Browser Reload action.
- `mobile/src/lib/devLane.ts` treats `devMode: "web"` or `platform: "web"` as a web-served status and therefore does not force Hermes.

Agent start path:

- `desktop/agent/devserver_http.go` accepts `surface`, `platform`, and `caller`.
- `desktop/agent/devserver.go` starts Expo with `npx expo start --web` when `opts.Platform == "web"`.
- Expo native/Hermes mode starts Metro with `npx expo start --dev-client`.
- Expo web sibling support exists: `StartWebPreview()` starts a separate `expo start --web` process on a `19006+` port while Metro continues serving Hermes.

This is the right product shape: Browser Reload should never require the guest app's native modules to match the Yaver host runtime.

### RN finding 1: `DevPreview.tsx` and `apps.tsx` still duplicate critical browser-lane logic

There are two active browser-preview implementations:

- `mobile/src/components/DevPreview.tsx`
- `mobile/app/(tabs)/apps.tsx`

`DevPreview.tsx` has richer structured progress handling:

- `progress` events,
- `phase` events,
- `snapshot.progress`,
- `snapshot.recentLogs`,
- heartbeat byte liveness via `lastByteAt`.

`apps.tsx`, which is the Projects-tab path in the screenshot, handles:

- `reload` / `ready`,
- `log`,
- `building`,
- `snapshot.recentLogs`,
- `heartbeat`,
- `error`.

It does not currently render structured RN/Metro progress from `progress`, `phase`, or `snapshot.progress`. So an RN-web compile can be alive and making progress, while the Projects overlay only shows sparse log tail or a generic heartbeat. This is the same drift class as the Flutter log issue.

Fix:

- Extract one browser-lane event reducer/parser shared by `DevPreview.tsx` and `apps.tsx`.
- The reducer should output:
  - recent log lines,
  - last byte time,
  - last output time,
  - current topic/phase/progress,
  - terminal error.
- Both screens should render from that reducer.

### RN finding 2: RN-web readiness had a real false-positive blank-screen bug, and the current fix is correct but must stay shared

`mobile/src/lib/previewReadyScript.ts` documents the RN incident:

- Expo Web's `index.html` can contain `<noscript>`, `<div id="root"></div>`, and a script tag before React mounts.
- The old readiness predicate accepted `body.children.length > 1`, so it hid the overlay before React rendered.
- That produced a blank RN-web screen with no retry or error because success had already latched.

The current predicate is correct in principle:

- Flutter engine markers are accepted.
- Flutter splash/script state is explicitly not accepted.
- `#root` / `#app` is ready only after it has children.
- Plain web keeps the original body heuristic.

Risk:

- Both browser-preview surfaces inject `PREVIEW_READY_SCRIPT`, which is good.
- Any future inline readiness probe would likely reintroduce the blank RN-web bug.

Fix:

- Keep `PREVIEW_READY_SCRIPT` as the only production readiness probe.
- Add a guard test or grep-based smoke that fails if `body.children.length > 1` readiness logic appears inline in preview surfaces.

### RN finding 3: bare React Native browser fallback is optimistic and can produce a fake web server

`ReactNativeDevServer.Start()` tries:

```sh
npx expo start --web
```

and falls back to:

```sh
npx react-native start
```

But bare `react-native start` is Metro for native bundles, not a browser-renderable web app. Its `BundleURL()` still returns `/dev/`. That can make status say "React Native is serving /dev/" when the operation behind it is not a web page.

This is the classic "inventory says yes, operation says no" shape.

Fix:

- For bare RN Browser Reload, require evidence of a web target before claiming browser support:
  - `react-native-web` dependency,
  - `react-dom` dependency,
  - Expo web entry/config,
  - or a known web bundler script.
- If the Expo web start fails and no web target exists, return a structured unsupported error:
  - "Bare React Native has no browser target; use Hermes Reload or add react-native-web/react-dom."
- Do not fall back to native Metro and advertise `/dev/` as browser-renderable.

Tests:

- Bare RN fixture without `react-native-web`: Browser Reload must fail before opening WebView.
- Bare RN fixture with web deps: Browser Reload can start.

### RN finding 4: project preview capabilities do not currently classify Expo/RN as browser-renderable

`desktop/agent/project_preview_capabilities.go` says `browserRenderableFramework()` includes:

- `flutter`,
- `nextjs`,
- `vite`,
- `react`,
- `web`,
- `astro`,
- `remix`.

It does not include `expo` or `react-native`.

That can conflict with the mobile UI, which always offers Browser Reload for all stacks after local composition and then asks the agent for preview options. Depending on how `applyPreviewCapabilities()` maps the agent answer, a newer agent may strip or reorder Browser Reload for RN/Expo even though `startDevServer({ web: true })` can serve Expo web.

This needs a more nuanced answer than simply adding RN:

- Expo can be browser-renderable if Expo web deps/config exist.
- Bare RN is browser-renderable only with `react-native-web` and `react-dom` or an explicit web script.
- RN without web target should default to Hermes.

Fix:

- Replace framework-only `browserRenderableFramework()` for RN/Expo with a disk probe:
  - `expo` + web capability,
  - bare RN + web deps/script,
  - otherwise unsupported with a concrete reason.
- Return that reason in project preview options so mobile can show "Browser Reload unavailable: no web target" instead of offering a dead lane.

### RN finding 5: `/dev/events` failures are still too quiet in the Projects path

In `apps.tsx`, the `/dev/events` fetch swallows:

- non-OK HTTP responses,
- missing `res.body`,
- parse failures,
- network failures.

For RN/Expo web, this is especially painful because Metro can be alive but noisy/large/slow. If the log stream itself is unauthorized or broken over relay, the overlay still looks like a compile problem.

Fix:

- In the shared parser/listener, push explicit diagnostic lines:
  - `/dev/events HTTP 401`,
  - `/dev/events HTTP 404 - remote agent too old or route missing`,
  - `/dev/events connected; waiting for frames`,
  - `/dev/events stream ended`.
- Treat connection-open as transport proof-of-life, separate from subprocess output.

### RN finding 6: Expo web sibling status can be invisible to the mobile Projects preview

The Go agent can run Metro and an Expo web sibling at the same time:

- Metro is primary `Port`.
- Expo web sibling is `WebPort`.
- `/dev-web/*` proxies to `WebPort`.

The Projects WebView path builds `bundleUrl` from `devStatus.bundleUrl` and generally loads `/dev/`. If an Expo project is in dev-client mode with a sibling web preview, the correct browser URL may be `/dev-web/`, not `/dev/`.

The code comments say clients that want browser preview should read `WebPort` and route through `/dev-web/*`. Verify `apps.tsx` does this in the rendered URL builder; if it does not, RN/Expo browser preview can hit Metro instead of Expo web.

Fix:

- Centralize `browserPreviewUrl(status, baseUrl)`:
  - if `status.webPort > 0`, use `/dev-web/`,
  - otherwise use `status.bundleUrl || "/dev/"`.
- Use it in both `DevPreview.tsx` and `apps.tsx`.

### RN finding 7: structured progress exists agent-side but is underused in Projects

`desktop/agent/devserver_progress.go` parses:

- modern Metro lines like `iOS node_modules/... 44.4% (667/1025)`,
- bare RN `Bundling: [...] 68%`,
- Expo/webpack module counts,
- Hermes byte generation,
- Flutter phase markers.

This is good. It means the agent can already tell the user "Metro is at 44%" instead of "waiting". The Projects overlay should render those fields the same way `DevPreview.tsx` does.

Fix:

- After sharing the event reducer, add a compact progress row to the Projects overlay:
  - topic label,
  - phase,
  - percent when exact,
  - current file tail.

### RN Acceptance Criteria

- Browser Reload for Expo/RN never triggers `/dev/build-native`.
- Hermes Reload for Expo/RN never opens WebView.
- Bare RN without a web target does not show Browser Reload as supported.
- RN-web preview does not hide the overlay until `#root` / `#app` has rendered children.
- Projects and DevPreview render the same logs/progress from the same event reducer.
- If `/dev/events` breaks, the user sees the stream failure and both app/agent versions.
- Expo web sibling previews load `/dev-web/` when `webPort` is present.

## Source Audit Findings

### High: Expo/RN browser preview ignores `webPort`, so it can load Metro instead of Expo Web

Evidence:

- `desktop/agent/devserver_http.go` starts an Expo web sibling for Web Reload and says clients should use `/dev-web/` when `webPort` exists.
- `desktop/agent/devserver_http.go` exposes `/dev-web/*` as the proxy to the sibling Expo Web server.
- `mobile/app/(tabs)/apps.tsx` computes the WebView URL only from `devStatus.bundleUrl || "/dev/"`.
- `mobile/src/components/DevPreview.tsx` does the same.

Impact:

- For Expo/RN browser previews, the agent can correctly start the Expo Web sibling, but mobile still loads `/dev/`.
- `/dev/` points at the primary dev server proxy, which can be Metro/native-bundle oriented depending on mode.
- Result: Browser Reload can show a blank page, 404/503 loop, or a native Metro response instead of the actual Expo Web app.

Fix:

- Add one shared helper:

```ts
function browserPreviewPath(status: DevServerStatus): string {
  return status.webPort && status.webPort > 0 ? "/dev-web/" : (status.bundleUrl || "/dev/");
}
```

- Use it in both `apps.tsx` and `DevPreview.tsx`.
- Add a unit test: `webPort=19006` must produce `/dev-web/`.

### High: Bare React Native fallback can advertise a browser dev server that is not browser-renderable

Evidence:

- `ReactNativeDevServer.Start()` first tries `npx expo start --web`.
- If that fails, it falls back to `npx react-native start`.
- `ReactNativeDevServer.BundleURL()` still returns `/dev/`.

Impact:

- Bare Metro is not a web app. Falling back to native Metro while still returning `/dev/` makes the status look browser-renderable.
- The phone can open WebView and retry forever against a server that cannot serve HTML.

Fix:

- Before Browser Reload for bare RN, require a browser target:
  - `react-native-web` and `react-dom`,
  - or an explicit web script / Expo web config.
- If no web target exists, reject Browser Reload with a structured reason and keep Hermes/WebRTC available.

### Medium: Projects preview still loses structured progress compared with `DevPreview`

Evidence:

- `DevPreview.tsx` handles `progress`, `phase`, `snapshot.progress`, `snapshot.recentLogs`, and `heartbeat`.
- `apps.tsx` handles `log`, `building`, `snapshot.recentLogs`, `heartbeat`, `ready`, and `error`, but not `progress`, `phase`, or `snapshot.progress`.

Impact:

- RN/Expo/Metro progress can be available from the agent but invisible in the Projects overlay.
- The screen can still feel stuck even though the box is producing exact progress.

Fix:

- Extract a shared browser-preview event reducer for both screens.
- Render current phase/progress/current file in the Projects overlay.

### Medium: Preview capability model treats RN/Expo browser support as framework-only instead of disk-capability based

Evidence:

- `browserRenderableFramework()` excludes `expo` and `react-native`.
- The RN/Expo branch still adds `PreviewOptionDevServer` unconditionally.
- Mobile composes Browser Reload for all stacks before applying agent capabilities.

Impact:

- The same project can be presented inconsistently across surfaces.
- RN without web deps may still expose Browser Reload; Expo with valid web support may not be marked as browser-primary when that is the user's chosen lane.

Fix:

- Add disk probes for RN/Expo web support.
- Return explicit supported/unsupported reasons per preview option.

### Medium: `/dev/events` streaming fix exists, but should be enforced by tests across all call sites

Evidence:

- `mobile/src/lib/sseClient.ts` correctly documents and fixes the RN fetch streaming problem via XHR.
- `apps.tsx`, `DevPreview.tsx`, and `quic.ts::subscribeDevEvents()` now use `subscribeSse`.
- A pure `sseClient.test.ts` covers chunk framing.

Impact:

- This is the right fix, but the historical bug came from three separate implementations drifting.

Fix:

- Add a grep-style test that fails if mobile code reads `res.body?.getReader()` for SSE.
- Add a focused test for non-2xx `/dev/events` surfacing as an overlay log line.

### Low: Shared banner now shows agent version, but Devices tab duplicates version display elsewhere

Evidence:

- `RemoteBoxBanner` now renders `agent v...` from live `/info.version` or `activeDevice.agentVersion`.
- `hotreload.tsx` also passes an extra chip with `Go agent ...`.
- `DeviceDetailsModal` has its own `Yaver version` row.

Impact:

- This is not a correctness bug, but the same version fact can appear twice on screens that pass their own `extra`.

Fix:

- Keep the shared banner chip as the default.
- Remove per-tab duplicate version chips where the shared banner already renders it.
